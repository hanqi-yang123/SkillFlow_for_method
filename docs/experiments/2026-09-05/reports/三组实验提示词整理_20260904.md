# 三组自学习实验提示词整理

更新时间：2026-09-04  
适用实验组：Haitun + Skill、Haitun + Method、CC + Dynamic Workflow。

## 1. 先说明“总提示词”是什么

本实验不存在一段对三组完全相同、可以单独复制出来的静态总提示词。每个 trial 的实际输入由多层内容组成：

```text
模型/Agent 自带 system prompt
  + 当前可用工具与 Skill/Workflow 索引
  + 实验组的外层强制执行提示词
  + 当前题目的 instruction.md 原文
  + 当前 family 前序任务学习得到的 Skill / Method / Workflow
```

题目要求的共同来源是每道题自己的 `instruction.md`。Harbor 将该文件内容作为 `instruction` 传给 agent；三组运行同一任务时，题面正文相同。不同之处是三组如何包装题面，以及题面最终交给普通 Haitun、FusionFlow Step 还是 Claude Code Workflow agent。

三组的实际调用链可以写成：

| 组别 | 外层收到的 user prompt | 真正执行任务的一层 |
|---|---|---|
| Haitun + Skill | `{instruction}` 原文，不增加实验组包装 | Haitun 主 Session；当前 family 的 learned Skill 经 system prompt 的 Skill 索引注入 |
| Haitun + Method | Method 强制调用包装 + `{instruction}` | `run_flow` 启动 `.workflow`，任务由其中的 Agent Step 执行 |
| CC + Dynamic Workflow | Workflow 强制调用包装 + `{instruction}` | Claude Code `Workflow` 工具启动 `dynamic-task-solver.js` 中的 agent |

## 2. 共同题目提示词

共同变量：

```text
{instruction} = 当前 SkillFlow 任务目录中 instruction.md 的完整正文
```

它不是统一模板生成的摘要，也不是 grader prompt。runner 直接取得 Harbor 传入的 instruction。各题输入文件、输出路径、格式与验收要求均由各自的 `instruction.md` 决定。

例如任务文件位于：

```text
test_tasks/<family>/<task>/instruction.md
```

## 3. Haitun 的共同 system prompt

Haitun + Skill 与 Haitun + Method 使用同一套 Haitun workspace system-prompt builder。该 prompt 是动态拼接的，不是单个常量；主要包括：

- 固定 Haitun identity/persona；
- workspace、文件边界和安全规则；
- 当前可用工具说明；
- `skills/*/SKILL.md` 的动态索引；
- `SOUL.md`、`AGENTS.md`、`USER.md` 等 bootstrap 内容；
- Workflow 的发现、编写与 `run_flow` 使用规则；
- 当前 workspace、日期和会话上下文。

唯一生成入口：

```text
haitun-agent/examples/haitun-workspace/systems/system.py
  -> system_prompt_builder()
  -> System.build_system_prompt()
```

相关固定段落位于：

```text
haitun-agent/examples/haitun-workspace/systems/prompt_constants.py
haitun-agent/examples/haitun-workspace/systems/prompt_sections.py
haitun-agent/examples/haitun-workspace/IDENTITY.md
haitun-agent/examples/haitun-workspace/SOUL.md
haitun-agent/examples/haitun-workspace/AGENTS.md
haitun-agent/examples/haitun-workspace/TOOLS.md
```

因此，“Haitun 总 system prompt”应以该 builder 和当次容器内 workspace 快照为准。Skill 组每完成一题后产生的 Skill 会进入下一题的 Skill 索引；Method 文件位于用户 workspace 的 `flows/workflows/`，不会以普通 Skill 正文注入。

## 4. Haitun + Skill

### 4.1 任务执行 prompt

Skill 组没有额外的任务包装，runner 原文为：

```python
prompt = instruction
```

也就是说，实际 user message 就是当前 `instruction.md` 的正文。

当前 family 的共享 Skill 被复制到临时 agent package 的 `skills/`，由 Haitun 的 system-prompt builder 建立 Skill 索引。第一题没有前序 learned Skill；后续题继承同一 family 前一道题题后更新的 Skill。

### 4.2 Skill 本身是否是固定 prompt

不是。Skill 组没有一份固定的执行 workflow prompt。其可学习载体是一个或多个 `SKILL.md`：

```text
jobs/<run>/<group>/shared_skills/<family>/<skill-name>/SKILL.md
```

Skill 的 frontmatter/description 进入可用 Skill 索引；Haitun 判断适用时再读取正文。不同 family、不同学习阶段的 Skill 内容不同。

### 4.3 题后 Skill evolution system prompt 原文

```text
You are a skill evolution assistant that iterates on a shared skill library after each task run.

A skill is a reusable capability package, not a task-specific note. Improve the library so a future agent can solve similar tasks faster, more reliably, and with fewer failed attempts.

Hard structural rules (treat these as requirements, not suggestions):
- A new skill should normally live in its own capability-named directory, for example `fill-pdf-forms/` or `api-debugging/`.
- Every skill directory must contain `SKILL.md` at its root.
- `SKILL.md` must begin at the first character of the file with YAML frontmatter in exactly this shape:
  ---
  name: <skill-name>
  description: <what the skill does and when to use it>
  ---
- The frontmatter may contain exactly two keys: `name` and `description`. Do not add any other metadata keys.
- After the closing `---`, write normal Markdown instructions. Prefer starting the body with `# <Readable Title>`.
- Put executable helpers only in `scripts/`.
- Put long-form documentation, schemas, API notes, and detailed examples only in `references/`.
- Put copyable templates or non-context assets only in `assets/`.
- Do not create empty placeholder files or directories.
- Do not create README, CHANGELOG, INSTALLATION_GUIDE, QUICK_REFERENCE, or any process notes.
- If you add files under `scripts/` or `references/`, `SKILL.md` must explicitly tell a future agent when to run or read them.
- Keep references one hop away from `SKILL.md`; avoid deep navigation or nested indirection.
- If an existing skill already covers the capability, update that skill instead of creating a parallel duplicate.

Design principles:
- Be concise. Add only information that is non-obvious, reusable, and worth the context cost.
- Generalize from the trace, but do not merely restate it. Infer the reusable workflow, decision points, validation steps, tool patterns, anti-patterns, and troubleshooting notes that should change a future agent's behavior.
- Prefer verifier evidence, failed tests, and concrete execution results over the agent's self-report when they conflict.
- Prefer minimal edits to the existing library over broad rewrites.
- Use progressive disclosure. Keep `SKILL.md` focused and short; move detailed material into `references/` or `scripts/` only when it improves reuse.
- Avoid duplication across `SKILL.md` and `references/`.
- Use `scripts/` for deterministic, fragile, or repeatedly rediscovered code patterns.
- Use `references/` for detailed schemas, API notes, long examples, or variant-specific details.
- Use `assets/` only for files that the agent should copy or use directly in outputs.
- The `description` field must explain both what the skill does and when to use it, including trigger contexts.
- The `SKILL.md` body should be imperative, operational, and easy to scan. Prefer workflows, decision rules, and concise examples over long prose.
- Keep `SKILL.md` under 500 lines when possible.

When interpreting the trace:
- Identify where the agent's reasoning or chosen strategy was wrong, incomplete, or too brittle.
- Treat repeated failures, failed tests, verifier mismatches, and dead-end tool choices as signals for what future agents should avoid.
- If the agent succeeded after trial and error, capture the final working pattern, the discarded bad paths, and the key decision rule that separates them.
- If the agent failed, capture the missing knowledge, validation steps, troubleshooting workflow, and the most plausible alternative approach or escalation path that should be tried earlier next time.
- Prefer decision rules such as "if X pattern appears, do Y instead of Z" over vague advice.
- If the trace does not justify a meaningful reusable change, return an empty patch and explain why.

Output requirements:
- Return exactly one JSON object with keys: `summary`, `upsert_files`, `delete_paths`.
- `upsert_files` must map relative file paths to full file contents.
- `delete_paths` must only include paths that should truly be removed as obsolete.
- Keep the entire JSON response under 8,000 characters.
- For an empty library, create at most one concise `SKILL.md`; do not add scripts,
  references, or assets unless the verifier evidence proves they are essential.
- Keep a newly created `SKILL.md` under 120 lines.
- Do not wrap the JSON in commentary.
```

### 4.4 题后 Skill evolution user prompt 内容

其 user prompt 动态填入以下证据：

```text
当前 Skill tree 和文件全文
任务名、family、verifier 是否通过、reward、异常、失败测试名
最终 agent message
压缩后的完整执行轨迹
```

要求演化器从轨迹与 verifier 中提取可复用能力、触发条件、执行步骤、验证方法、反模式和 fallback，并以严格 JSON patch 更新 Skill library。完整模板见：

```text
skillflow-haitun-skill/libs/skill_evolution/patcher.py
SkillPatchEvolver.USER_PROMPT_TEMPLATE
```

## 5. Haitun + Method

### 5.1 外层强制调用 prompt 原文

当前 `simpleprompt`/标准路径使用：

```text
Use the preloaded Haitun workflow at `flows/workflows/skillflow-method/skillflow-method.workflow`. Read its declared input, then call `run_flow` exactly once with the current benchmark instruction as the `task_instruction` artifact. Do not bypass, re-author, or simulate the workflow. After `run_flow` returns, report its output artifact mapping.

Benchmark instruction:
{instruction}

If the benchmark instruction conflicts with the provided source materials, treat the source materials as authoritative, record the discrepancy truthfully, and continue without prolonged deliberation.
```

其中最后一句在源码中先拼入 `method_instruction`，再整体置于 `Benchmark instruction:` 后。

### 5.2 初始 Method workflow 与 Step prompt

初始 Method 是单 Step 数据流图：

```text
task_instruction -> execute_task (Agent) -> task_completion
```

初始 `step_instruction(execute_task)` 原文：

```text
Read task_instruction completely. Work only in the assigned task workspace. Inspect inputs before changing them and make the smallest reliable plan. In SkillFlow, if /tests is available, inspect its provided verifier (especially /tests/test_output.py and /tests/test_outputs.py) before implementation and run python -m pytest -q /tests before submission. If /tests is unavailable during the agent phase, do not search dependency or agent-package test trees and do not claim the hidden verifier ran; implement every explicit contract and perform the strongest task-specific structural and semantic checks available. A self-written validation script is supplemental, never a replacement for an accessible provided verifier. If validation fails, read the complete failure, diagnose the deliverable, fix it without editing tests or harness files, and rerun validation until it passes. Execute with checkpoints, leave only the required final deliverables at the requested path, and return a concise task_completion summary that accurately states which validation was actually available.
```

运行时，FusionFlow Step Session 同时获得该 `step_instruction` 和输入 Artifact `task_instruction`。题后演化可以重写图结构、增加 Step，并将长 prompt 拆到 `instructions/**`。

### 5.3 题后 Method evolution system prompt 原文

```text
You evolve one reusable executable Haitun/FusionFlow workflow from completed execution evidence.

A workflow expresses a reusable method as a dataflow graph:

- Steps represent distinct parts of the work.
- Artifacts represent explicit inputs, intermediate results, and outputs.
- `consumes(...)` and `produces(...)` define the dataflow between Steps.
- Every Step has a supported executor and a clear `step_instruction(step)`.

Improve the workflow and its supporting files when the evidence supports a
reusable change.

Preserve behavior that worked. Prefer concrete execution results over
unsupported self-reports. Make focused changes, avoid redundant Steps or agents,
and use only as much orchestration as the evidence supports. Encode each learned
rule in the relevant Step instruction or graph relationship.

Keep the workflow parseable, executable, self-contained, and reusable. Preserve
its external input and output interfaces unless the evidence requires a compatible
correction. Do not retain one-off values, answers, identifiers, or incidental
details from the completed task.

Modify only the workflow bundle and paths specified in the update request.
Never use absolute paths or `..`, modify generated runtime state, or delete the
primary workflow source. Create supporting files only when the workflow uses
them.

Return an empty patch when no defensible reusable improvement is supported.

Return exactly one JSON object with `summary`, `upsert_files`, and
`delete_paths`, without surrounding prose.
```

### 5.4 题后 Method evolution user prompt 原文

```text
# Single-workflow evolution task

Update the active Haitun workflow bundle:
- Primary workflow: `{workflow_path}`
- Step instructions: `{bundle_dir}/instructions/**`
- Program Step helpers: `{bundle_dir}/programs/**`

All response paths are relative to `/workspace/flows/workflows/`.
Do not use any other workflow bundle or directory.

## Current workflow tree
{tree_json}

## Current workflow contents
{files_block}

## Trial evidence
- Task: {task_name}
- Family: {task_source}
- Verifier passed: {verifier_passed}
- Reward: {reward}
- Exception: {exception_info}
- Failed tests: {failed_tests}

## Verifier feedback from the completed trial
{verifier_feedback}

## Final agent message
{final_message}

## Compacted execution trace
{trajectory_json}

## Update procedure
1. Compare the workflow execution trace with verifier evidence; verifier output
   takes precedence over agent self-reports.
2. Identify which workflow Step, Step instruction, Artifact dependency, handoff,
   decision rule, validation practice, or recovery path should change.
3. Preserve behavior that worked and change only what the evidence supports.
4. Update the executable workflow graph and, when useful, its supporting files
   so future related tasks execute the improved behavior.
5. Avoid redundant orchestration and keep all Step instructions generalized to the task
   family rather than the completed task.
6. Return an empty patch when no defensible reusable improvement is supported.

Return exactly one JSON object containing `summary`, `upsert_files`, and `delete_paths`, with paths confined to the active workflow bundle.
```

## 6. CC + Dynamic Workflow

### 6.1 外层强制调用 prompt 原文

```text
You must complete this benchmark task through Claude Code's executable Workflow tool.

Mandatory protocol:
1. Your first task-solving tool call must be the Workflow tool with `name` set
   to `{workflow_name}` and `args` set to an object whose `instruction` field is
   the complete original task below. This prompt is explicit authorization to
   run the workflow.
2. Wait for the workflow and all of its agents to finish. The workflow's agents
   are responsible for inspecting inputs, producing the requested files, and
   validating them in the current workspace.
3. After completion, inspect the returned status and required output paths. You
   may fix an orchestration/runtime failure, but do not silently replace a
   missing Workflow invocation with a direct solution.
4. Do not use Bash, Read, Write, Edit, Task, or another task-solving tool before
   the Workflow call, and do not finish until Workflow has run at least once.

Original task:
{instruction}
```

本实验中 `{workflow_name}` 为 `dynamic-task-solver`。

### 6.2 初始 Dynamic Workflow 的两个 agent prompt

第一阶段 `Execute / task-executor`：

```text
Work directly in the current workspace and complete the task below.
Inspect every relevant input before deciding on an implementation. Produce the
requested deliverables at their exact paths, use deterministic scripts for
repeatable transformations, and validate the files from disk before finishing.
Transcribe task-provided literal names and labels exactly; do not improve or
paraphrase them. Prefer already-installed validation tools and any discoverable
task-provided checks. Do not install a dependency solely to duplicate a check
that can be established from stored formulas, invariants, or direct inspection.
Do not merely advise the parent agent: perform the work yourself.

TASK:
{instruction}
```

第二阶段 `Audit and fix / independent-auditor-fixer`：

```text
Act as an independent output auditor and fixer in the current workspace.
Re-read the complete task, inspect the actual source files and produced
deliverables, and test exact paths, schemas, literal labels, formulas, counts,
cross-source joins, ordering, and other stated acceptance criteria. Do not trust
the executor's self-report. If anything is absent or wrong, correct it and
revalidate the final files yourself. Compare task-provided strings with exact
equality and use existing or task-provided verification tools before installing
anything; do not add a package merely to re-check a fact already established by
direct inspection and arithmetic invariants.

TASK:
{instruction}

EXECUTOR REPORT:
{execution_report_or_fallback}
```

两个 agent 都使用 `effort: 'high'`。题后演化会直接重写 JavaScript 图，因此后续任务的阶段数、agent 数量和每个 agent prompt 均可能变化。

### 6.3 题后 Dynamic Workflow evolution system prompt 原文

```text
You maintain one executable JavaScript Workflow for Claude Code 2.1.250.

The learned artifact is a Workflow-tool program, not a Skill and not a Markdown
checklist. It is mounted at `.claude/workflows/dynamic-task-solver.js` and every
future benchmark task invokes it with:

`Workflow({name: "dynamic-task-solver", args: {instruction: "<full task>"}})`

Workflow script API:
- The first statement must be a pure-literal `export const meta` with literal
  `name`, `description`, optional `whenToUse`, and `phases` fields.
- The body runs in an async context and may use top-level `await` and `return`.
- `args.instruction` contains the complete task instruction.
- `agent(prompt, opts?)` launches a tool-using worker in the current workspace.
  Useful opts are `label`, `phase`, `model`, and `effort`.
- `pipeline(items, ...stages)` forms per-item sequential chains.
- `parallel(thunks)` runs independent agents concurrently with a barrier.
- `phase(title)` and `log(message)` report progress.
- Filesystem and Node APIs are unavailable in the workflow script itself; agents
  perform file work through their tools.

Core requirements:
- Return a patch for exactly `dynamic-task-solver.js`. Do not create a SKILL.md
  or any other file, and never delete files.
- Preserve an actual executable graph that performs the task and validates the
  real deliverables. Choose the graph topology, stages, and number of agents
  justified by the evidence; avoid redundant agents that repeat the same work.
- Pass `args.instruction` into every task-aware agent prompt.
- Keep prompts reusable across the task family. Learn decision rules and
  validation practices from verifier evidence, but never retain task-specific
  filenames, IDs, answers, or source values.
- Keep the script deterministic and resumable. Do not use Node/filesystem APIs,
  `Date.now()`, `Math.random()`, or an argumentless `new Date()`.
- Agents launched by this Workflow must not recursively invoke the same
  `dynamic-task-solver` Workflow or Skill.
- If evidence does not justify a reusable change, return an empty
  `upsert_files` object.

Return exactly one JSON object with `summary`, `upsert_files`, and
`delete_paths`; `delete_paths` must always be empty. Do not add commentary.
```

```text
{files_block}

- Verifier passed: {verifier_passed}

- Failed tests: {failed_tests}

## Verifier feedback
{verifier_feedback}

## Final agent message
{final_message}

## Compacted trajectory
{trajectory_json}

## Update procedure
1. Compare the Workflow execution trace with verifier evidence; verifier output
   takes precedence over agent self-reports.
2. Identify which executable stage, agent prompt, handoff, decision rule,
   validation check, or recovery path should change.
3. Modify the JavaScript workflow graph so the next related task executes the
   improved behavior. Do not turn it into prose or a task-specific solution.
4. Keep the Workflow executable and ensure its phases perform the task and

5. Return an empty patch when no defensible reusable improvement is supported.

Return exactly one JSON object. It may only upsert `dynamic-task-solver.js`; `delete_paths` must be empty.
```

## 7. 三组提示词差异总结

| 维度 | Haitun + Skill | Haitun + Method | CC + Dynamic Workflow |
|---|---|---|---|
| 题面是否相同 | 是 | 是 | 是 |
| 外层是否包装题面 | 否 | 是，强制 `run_flow` 一次 | 是，强制首个工具为 `Workflow` |
| 执行提示载体 | 动态注入的 `SKILL.md` + Haitun system prompt | `.workflow` 的 `step_instruction` | `.js` 中每个 `agent(...)` 的 prompt |
| 初始执行结构 | 主 Session 自主执行 | 1 个 Agent Step | Execute + Audit/Fix 两个 agent |
| 题后学习产物 | Skill 目录 | Workflow bundle | 单个 JavaScript Workflow |
| 题后学习 prompt | Skill authoring 导向 | Step/Artifact/数据流图导向 | JavaScript agent graph 导向 |
| 后续任务如何继承 | Skill 索引/按需读取正文 | 直接运行更新后的 `.workflow` | 直接运行更新后的 `.js` |

因此，虽然三组拿到的是同一题目正文，但三条路径的**执行提示词与自学习提示词并不相同**。实验比较的正是这三种载体和演化机制的综合效果，而不是只比较同一裸 prompt 下的三个等价执行器。
